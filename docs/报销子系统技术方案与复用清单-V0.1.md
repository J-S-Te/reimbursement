## 0. 摘要

1. 报销子系统当前是"只有设计稿、零代码"：仓库 6 个文件，无 go.mod、无 package.json、无 migrations、无测试、无 CI，明确不可验收（NOT READY）。
2. 开发形态：第 8 个独立业务子系统——Go API + 独立后台 worker + 独立 MySQL schema + 统一前端第 8 个模块，不并入 contract_management。
3. 合同管理可复用的是"平台接入方式 + 工程骨架 + 安全生产件 + 若干引擎结构"；不可复用其领域实现（表结构、状态机、签署/文档、SELF-only 数据范围、全局单行编号语义）。
4. 审批状态机采用 DB-first（单事务状态机 + 审批快照 + 幂等命令 + outbox），Temporal 只承担催办/重试/归档打包等短异步；不照搬合同"审批态在工作流内存"的实现。
5. 开工前有 6 个 P0 阻塞与 8 项待拍板决策：

   | # | P0 阻塞 | 为什么阻塞 |
   |---|---|---|
   | P0-1 | 需求基线缺失（《需求规格说明书 V1.1》不在工作区） | FR-1.1~FR-8.3、BR-4/5/8 无源可查，验收口径不存在 |
   | P0-2 | 发票 OCR / 税务验真 Provider 不存在（平台与 6 个子系统均无） | FR-2.2/2.3/2.4 是核心风控，无法验收 |
   | P0-3 | 成本中心主数据不存在（原型自标前置 Blocker） | 主中心决定部门负责人节点，路由与归档均依赖 |
   | P0-4 | 审批人无法范围化解析（合同只能按 role_code 全租户解析） | 部门/团队负责人审批会变成"任意同角色可审" |
   | P0-5 | 状态机语义冲突（ER 4 态 / 原型 6 态 / 存在可达死状态） | 状态、节点、线路不定，建库即返工 |
   | P0-6 | 平台接入 6 件事未纳入计划 | 缺一项就无法登录 / 许可失效 / 审计 503 / 前端 404 |

   上述 6 项与第 7 节 D1-D8 决策，是"可以开始编码"的先决条件。

### 2.4 两版流程图差异（决定验收基线）

| 环节 | 手工版 | AI 版 | 影响 |

## 3. 目标架构

### 3.1 形态与上下文

~~~text
员工/审批人/财务/出纳
   |
   v
统一前端 reimbursement 模块 (/reimbursement)
   |
   v
reimbursement-api --+--> 独立 MySQL schema（业务行带 tenant_id）

   ^
   | 短异步指令
reimbursement-worker -- outbox 投递、SLA 催办、OCR/验真重试、归档打包
~~~

平台已提供、不需要自建：OIDC 登录与本地会话、授权上下文（角色/权限/数据范围）、应用注册与许可运行时、审计摄取、通知摄取、文件网关、子系统会话治理、权限目录发布。

### 3.2 分层与依赖规则

~~~text

  worker/           后台任务入口
~~~

1. handler 不得直接调用仓储，只能经 application 用例。

3. 跨域只经端口/事件，不跨域直接读表。
4. 所有写路径带 expected_version；所有可重复提交的命令带幂等键。
5. 禁止 AutoMigrate；迁移与权限清单版本一起发布。

## 4. 关键设计

### 4.1 报销单状态机（建议替代原型的 6 态）

~~~text
DRAFT --submit--> IN_APPROVAL --approve(all)--> APPROVED_PENDING_PAYMENT --pay--> PAID --archive--> ARCHIVED
  ^                    |    |                          |
  |                    |    +--reject/return--> RETURNED --改后重提--> IN_APPROVAL
  |                    +--withdraw(仅申请人)--> DRAFT
  |                    +--void(草稿/退回)--> VOID
~~~

设计要点：
1. 删除"已通过"独立状态，用 APPROVED_PENDING_PAYMENT 表达"审批完成待付款"。
2. 付款不是审批节点：出纳不能在审批页"通过"；付款是独立动作，只允许从 APPROVED_PENDING_PAYMENT 发起。
3. 从根上消除 EX-1 的死状态（"已通过"后永远无法付款）。
4. 单据号在提交时同事务分配（草稿可空号），不复用合同"审批完成取号"语义。

### 4.2 发票状态机

~~~text
UPLOADED -> OCR_PROCESSING -> (OCR_FAILED | OCR_DONE) -> VERIFYING
         -> (VERIFIED | MISMATCH | NOT_FOUND | EXPIRED | DUPLICATE_BLOCKED)
         -> LINKED -> USED
异常：OCR_FAILED / MISMATCH / NOT_FOUND / EXPIRED -> 异常池 -> 人工查验 -> MANUALLY_VERIFIED（带原因+证据+审计）
~~~

关键点：发票异常是发票状态，不是报销单状态（原型把异常当作报销单状态，导致单据语义混乱）。

### 4.3 审批节点与命令

| 项 | 设计 |
|---|---|
| 节点码 | 稳定英文 code，中文仅展示（避免"会计/财务合规性/出纳付款"三套命名） |
| 命令集 | approve / reject / return / add_sign / transfer / withdraw / urge / comment |
| 命令幂等 | 每命令 command_id 唯一，重复提交不重复生效 |
| 受理人校验 | 动作时校验"当前节点受理人 = 操作人" + 节点代次 + 单据状态 + expected_version |
| 申请人隔离 | 申请人不得审批自己的单据（任何节点），源自合同硬校验 |
| 审批人解析 | 提交时按部门/团队/项目 + 成本中心负责人解析；解析不到 422 fail-closed，不写审批实例 |
| 快照 | 提交时冻结：规则 ID+版本、节点列表、受理人、金额、标准版本、分摊、路由结论、内容 hash |
| SLA | 超期只标记 + 催办 + 升级，不自动通过/驳回（待 D4 裁决） |

### 4.4 付款与归档

| 项 | 约束 |
|---|---|
| 付款前置 | 单据必须为 APPROVED_PENDING_PAYMENT |
| 金额 | 实付默认 = 应付；差异必须填原因并二次确认（v1 建议禁止部分付款） |
| 流水号 | (tenant_id, serial_no) 唯一，防重复录入 |
| 幂等 | 付款请求带幂等键；并发付款仅一笔成功 |
| 不可变 | 付款记录只追加；已付款后业务字段拒绝 UPDATE/DELETE；更正走冲正事件 |
| 凭证 | 付款凭证走 File Gateway，只存 file_id |
| 归档 | 归档包 = 单 + 票 + 影像 SHA256 + 审批账本 + 付款记录；封包后只读 |
| 完整性 | 逐项校验，不得用"已付款条数比例"冒充完整性（原型缺陷） |
| 借阅 | 需审批 + 期限 + 到期回收 + 审计 |

### 4.5 数据模型硬约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | 金额一律 amount_minor BIGINT + currency CHAR(3) | 原型用 JS 浮点算总额；ER 用 decimal；合同已用整数分 |
| 2 | 全表 tenant_id / version / created_by / updated_by / 时间戳 | ER 全部缺失；平台要求业务行带 tenant_id |
| 3 | (tenant_id, claim_no) 唯一，提交时取号 | 原型在浏览器 max+1 拼号，并发必重号 |
| 4 | (tenant_id, invoice_code, invoice_no) 唯一 | 查重必须落 DB，不能靠前端提示 |
| 5 | invoice_binding 同一发票仅一条 ACTIVE | 防一票多报；释放留审计 |
| 6 | 分摊持久化 amount_minor + ratio_bp，金额合计=总额，尾差落主中心 | 原型只存比例现算，归档金额对不平 |
| 7 | (tenant_id, serial_no) 唯一 + 付款幂等键 | 防重复付款 |
| 8 | 标准/路由规则不可变版本 + 明细引用 standard_version / limit_snapshot_minor | 原型原地编辑，历史超标不可复算 |
| 9 | 审批账本 append-only + command_id 唯一 + origin revision | ER 用平台审计替代，证据链不足 |
| 10 | 不建跨库外键；项目/用户/部门仅存 ID | 平台数据边界 |

### 4.6 接口草案

| 场景 | 方法与路径 | 关键约束 |
|---|---|---|
| 建草稿 | POST /api/v1/claims | Idempotency-Key；数据范围 |
| 改草稿 | PUT /api/v1/claims/{id} | expected_version；仅本人/草稿态 |
| 提交 | POST /api/v1/claims/{id}/submit | 同事务：重算 -> 校验 -> 快照 -> 取号 -> 建审批 -> outbox；重复提交 409 |
| 审批命令 | POST /api/v1/approvals/{id}/commands | 受理人 + 代次 + 状态 + 幂等 |
| 付款 | POST /api/v1/payments | 状态前置 + 流水唯一 + 幂等 |
| 发票上传 | POST /api/v1/invoices/upload-sessions | 经 File Gateway；批量/大小上限 |
| 发票查询 | GET /api/v1/invoices | 范围下推 + 字段脱敏 |
| 归档 | POST /api/v1/archives/{id}/seal | 受控入口 + 完整性校验 |
| 导出 | POST /api/v1/exports | 异步任务 + 范围快照 + 公式注入防护 |

错误信封：{ code, message, details }，错误码稳定（INVALID_STATE / VERSION_CONFLICT / DUPLICATE_INVOICE / PERMISSION_DENIED）。

### 4.7 权限与数据范围

- 权限码按"资源.动作"命名：expense.claim.create、expense.approval.act、expense.payment.record、expense.config.manage、expense.invoice.manual_verify、expense.export。
- 数据范围：SELF（本人）+ ORG（部门/团队）+ PROJECT（所辖项目）+ APPLICATION（财务/出纳/审计全租户）。
- 合同仅有 SELF（permission-manifest.yaml:344 [已核验]），不足以支撑报销，必须扩展。
- 读路径在 SQL 层下推范围，禁止"先查全量再内存过滤"；列表与 COUNT 使用同一谓词。
- 字段级脱敏：金额、税号、收款账号、职级、OCR 原文、影像访问分别控制；参考 project_management 的 role+field -> *** 白名单模式。
- 前端菜单可见性不是授权执行点。

### 4.8 审计与事件

必须审计的动作：提交、撤回、审批、驳回、加签、转交、退回、付款、冲正、人工验真、配置变更、导出、下载、借阅、拒绝（403）。

规则：
1. 业务事务内写 audit_outbox，与业务同提交。
2. 审计投递不可用时请求 fail-closed 503（平台既有口径）。
3. 审计 payload 不含金额明文、税号明文、收款账号、OCR 原文；只记 ID/哈希/结果码。
4. 业务审批账本自持，平台审计只作外部补充，不可反向依赖。
