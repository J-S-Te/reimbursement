# 报销管理系统 · 角色与权限说明

> 权威来源：`reimbursement/authz/permission-manifest.yaml`（JSON 内容）、`reimbursement/authz/manifest_test.go` 断言、`.ai/qa/reimbursement-role-alignment-20261110/`、`docs/architecture/ADR-0001-permission-catalog-and-admin-role.md`。
> 当前目录版本：**catalog v4，9 个角色，32 条权限**。
> 本文说明"每个角色是干什么的、能做什么、明确不能做什么"，不替代方案原文与平台授权目录配置。

---

## 1. 先理解两个正交维度

报销系统的授权由**两层独立校验**共同决定，缺一不可：

| 维度 | 含义 | 来源 |
|---|---|---|
| **动作权限**（32 条） | "能不能执行这个动作" | 平台授权目录下发的 `permissions` |
| **数据范围** | "能对哪些对象执行" | 本地发布的 scope（`SELF` / 已发布组织 `ORG` / `TENANT_ALL`） |

关键原则（已由 `manifest_test.go` 与代码固化）：

- **不从角色名推断数据范围**：普通财务、审计、档案人员即使持有对应动作权限，没有发布 scope 也**看不到**跨组织数据。
- **管理员不隐式获得范围，也不获得自审自付权**：`reimbursement_admin` 的范围来自独立的 `expense.scope.tenant_all` 能力，而不是"因为他是管理员"；他仍然受职责分离约束。
- **权限通过平台目录发布生效**，本地 manifest 是契约；目录升版后必须重新发布（当前从 v3 升到 v4）。

## 3. 逐角色说明

### 3.1 `reimbursement_admin` 超级管理员

- **是干什么的**：本租户的业务配置与受控运维角色。配置费用标准、审批路由、公司主体、收款档案；发布版本化政策；处理对账与失败投递；接管失效审批待办。
- **能做什么**：全部 32 条权限，包括 `expense.config.manage`、`expense.policy.publish`、`expense.approval.recover`、`expense.integration.manage`、`expense.scope.tenant_all`。
- **明确不能做什么**：
  - 不能自审自付：`submit.go` 的节点自审校验、`payments.go` 的申请人自付校验对管理员同样生效；
  - 不能办理**未指派**给自己的审批任务（任务受理人约束）；
  - 不能绕开会计/出纳分离：即使有 `payment.record`，与会计审核人同一人仍被 `ACCOUNTANT_CASHIER_CONFLICT` 拒绝。
- **典型场景**：首次接入时发布目录与政策、开年调整标准、处理卡在失效审批人的待办。

### 3.2 `expense_applicant` 报销申请人

- **是干什么的**：录单的人。维护本人草稿、上传发票与证据、提交、撤回、作废本人未付款单据、人工复核本人发票、查询可关联项目、查看本人报销单。
- **持有权限**：`claim.read/update/create/submit/withdraw/void`、`invoice.read/upload/review`、`project.reference`、`archive.read`。
- **明确不能做什么**：不能审批（`expense.approval.act` 不在其内）；不能付款；不能跨人查看他人报销单；不能对已批准义务自行重开或作废（那是 `claim.reopen` / `claim.approved_void`，仅财务负责人持有）。
- **典型场景**：出差回来录一笔报销、补传发票、发现填错后撤回重提。

### 3.3 `expense_approver` 业务审批人

- **是干什么的**：按审批路由被指派任务后，办理自己名下那条审批任务。
- **持有权限**：只有 `expense.claim.read` + `expense.approval.act` **两条**。
- **为什么这么少**：审批人的授权范围由**任务分配**保证，而不是由权限条数保证。他能看到的是被指派任务对应的单据；`expense.approval.act` 也只对"当前受理人是他"的任务生效。
- **明确不能做什么**：不能主动挑单审批；不能转交（转交是协调人的 `approval.transfer`）；不能看到未指派的单据明细；不能审批自己提交的单据（`SELF_APPROVAL_FORBIDDEN`）。
- **典型场景**：收到待办通知 → 打开被指派任务 → 通过/驳回。

### 3.4 `expense_accountant` 会计

- **是干什么的**：财务复核与票据把关。核验票面、做财务审核、登记票据核验结论、批准票据重大更正与风险关闭、记录外部付款异常。
- **持有权限**：`claim.read`、`invoice.read`、`approval.act`、`finance.review`、`archive.read`、`invoice.verify`、`invoice.correct`、`payment.read`、`payment.exception.record`。
- **明确不能做什么**：不能登记付款（那是出纳的 `payment.record`）；不能批准冲正（那是财务负责人的 `reversal.approve`）；不能自己关闭自己记录的风险；不能批准自己发起的票据更正。
- **典型场景**：票据 OCR/查验不一致 → 人工核验并记录结论；发现红冲 → 登记风险并要求更正；对已批准单据的票据做重大更正时，作为独立批准人。

### 3.5 `expense_cashier` 出纳

- **是干什么的**：执行付款与发起冲正。登记线下付款事实、发起全额冲正请求、记录外部付款异常。
- **持有权限**：`claim.read`、`invoice.read`、`payment.record`、`payment.reversal.request`、`archive.read`、`payment.read`、`payment.exception.record`。
- **明确不能做什么**：不能审核自己的付款（`ACCOUNTANT_CASHIER_CONFLICT`：会计审核人必须独立于付款登记人）；不能批准冲正（只能申请）；不能修改已登记付款事实（只能走冲正）；不能给本人申请的单据付款（`SELF_PAYMENT_FORBIDDEN`）。
- **典型场景**：按已批准单据完成打款并登记流水号。

### 3.6 `expense_auditor` 审计员

- **是干什么的**：只读监督。查看审计账本、查看单据与发票、查看付款账本、导出证据包。
- **持有权限**：`claim.read`、`invoice.read`、`audit.read`、`archive.read`、`archive.export`、`payment.read`。
- **明确不能做什么**：没有任何写动作权限——不能改单据、不能审批、不能付款；数据范围仍需发布 scope，不是"审计就能看全租户"。
- **典型场景**：季度抽查、配合内审取证导出。

### 3.7 `expense_archive_operator` 档案管理员

- **是干什么的**：档案封存后的运维。查看档案、重试失败的归档、按封存版本创建证据包导出。
- **持有权限**：`claim.read`、`archive.read`、`archive.retry`、`archive.export`。
- **明确不能做什么**：不能改业务单据；不能删除/清理已封存档案（证据不可变）；导出的证据包下载时仍会**逐次重新鉴权**，撤权后立即失效。
- **典型场景**：档案封存缺件导致任务失败 → 重试；审计需要封存版本证据 → 建包并下载。

### 3.8 `expense_finance_director` 财务负责人

- **是干什么的**：财务侧的独立批准与政策发布。批准全额冲正、批准未付款义务的作废、重开待付款义务、发布版本化政策、独立核实外部付款异常。
- **持有权限**：`claim.read`、`approval.act`、`payment.reversal.approve`、`payment.read`、`archive.read`、`policy.publish`、`claim.reopen`、`claim.approved_void`、`payment.exception.review`。
- **明确不能做什么**：不能登记付款（不持有 `payment.record`）；不能做票据核验与更正批准（不持有 `invoice.correct`/`finance.review`）；冲正批准必须独立于申请人与原付款人（`REVERSAL_APPROVER_CONFLICT`）。
- **典型场景**：出纳发起冲正 → 财务负责人独立批准；历史尾款需要重开 → 重开并要求重新确认。

### 3.9 `expense_approval_coordinator` 受控审批转交协调人

- **是干什么的**：只处理审批任务的转交。当原审批人离职、撤权或长期不可用时，把任务转给合法替代人。
- **持有权限**：`claim.read`、`approval.act`、`approval.transfer`。
- **明确不能做什么**：不能转交不是自己当前受理的任务；目标必须同时满足"目录当前能力"与"本地有效替代映射"；**不获得任何财务范围**；不能替被转交人做出业务决定。
- **典型场景**：审批人离职 → 协调人把待办转给其上级或指定替代人。

## 5. 数据范围规则

- **`tenant_all`**：只有持有 `expense.scope.tenant_all` 的账号获得本租户完整对象范围（含未占用票据的读取）。当前目录中该能力**仅授予超级管理员**，且 `manifest_test.go` 断言其唯一性。
- **`ORG` 范围**：财务、审计、档案类角色必须由管理员发布明确的组织列表（`scopes` 配置），`financeScope`/`fullRead` 才按组织放行。**没有发布 scope = 看不到跨组织数据**，即使动作权限齐全。
- **`SELF` 范围**：申请人只能操作本人单据；`fullRead` 对本人申请人恒为真，但仅限本人单据。
- **跨租户一律拒绝**：所有查询带 `tenant_id`，跨租户返回 404（不泄露存在性）。
- 实现位置：`internal/application/access.go`（`financeScope`、`fullRead`）、`internal/identity/principal.go`。

## 6. 职责分离硬约束（代码强制，非配置项）

| 约束 | 错误码 | 位置 |
|---|---|---|
| 审批人不得与申请人重叠 | `SELF_APPROVAL_FORBIDDEN` | `internal/application/submit.go:451` |
| 申请人不能为本人登记付款 | `SELF_PAYMENT_FORBIDDEN` | `internal/application/payments.go:93` |
| 会计审核人必须独立于付款登记人 | `ACCOUNTANT_CASHIER_CONFLICT` | `internal/application/payments.go:100` |
| 申请人不能更正本人付款事实 | `SELF_REVERSAL_FORBIDDEN` | `internal/application/payments.go:316` |
| 冲正批准人必须独立于申请人与原付款人 | `REVERSAL_APPROVER_CONFLICT` | `internal/application/payments.go:350` |
| 票据所有人/申请人不能批准本人票据更正 | `SELF_FINANCIAL_ACTION_FORBIDDEN` | `internal/application/invoice_corrections.go:159`、`invoice_corrections_write.go:144` |
| 风险记录人不能自行关闭风险 | `SELF_FINANCIAL_ACTION_FORBIDDEN` | `internal/application/invoice_risks.go:148` |
| 票据所有人不能自行关闭财务复核 | `SELF_FINANCIAL_ACTION_FORBIDDEN` | `internal/application/invoice_risks.go:100` |
| 申请人不能自行重开/作废已批准义务 | `SELF_FINANCIAL_ACTION_FORBIDDEN` | `internal/application/claim_controls.go:71` |
| 审批任务只能由当前受理人办理 | 任务受理人校验 | `internal/application/approval.go`、`query.go` |

> 重要：这些约束**不因** `reimbursement_admin` 持有全部权限而放宽。超级管理员的"全量"体现在配置与范围能力上，不体现在"可以自己批自己"。

## 7. 典型流程与角色分工

```
申请人 ──录单/传票──► 提交
                        │
                        ▼
      审批路由（技术/销售/财务节点，按项目权威岗位生成）
                        │  审批人：只办被指派任务
                        ▼
                   会计财务审核（finance.review + 必要时 invoice.verify）
                        │
                        ▼
                出纳登记付款（payment.record）
                        │
              ┌─────────┴──────────┐
              ▼                    ▼
     财务负责人独立批准冲正    归档封存（不可变）
     （reversal.approve）          │
                                   ▼
                        档案管理员/审计导出证据包
```

| 环节 | 谁做 | 关键权限 |
|---|---|---|
| 录单与提交 | 申请人 | `claim.create/update/submit`、`invoice.upload` |

## 8. 常见误区

| 误区 | 事实 |
|---|---|
| "超级管理员就是业务配置管理员，不能审批付款" | 现行口径：`reimbursement_admin` 持有全部 32 条权限，**但**仍受自审/自付/会计出纳分离/任务受理约束。这是经裁决保留的口径，偏差与补偿控制记录在 `docs/architecture/ADR-0001-permission-catalog-and-admin-role.md`。 |
| "审批人权限少，所以做不了审批" | 审批人的范围由**任务指派**保证；`approval.act` 只对当前受理人有效，不需要更宽的读取权限。 |
| "有动作权限就能看全租户数据" | 不能。财务/审计/档案必须发布 scope；`tenant_all` 只授予超管。 |
| "档案导出后随时能下载" | 下载时逐次重新鉴权并复核内容哈希；超过保留期返回 `EXPIRED`，需重新生成。 |
| "冲正可以部分金额" | 不支持，只有全额冲正（含独立批准）。 |
